# Методика risk-score

Документ существует для одного: **обосновать цифру перед тем, кто платит
за неё**. Страховщик задаёт вопрос «почему вы написали 62?» — и ответ должен
быть в весах, в источниках и в ограничениях, а не в уверенном тоне.

Действующая версия весов: **`score_version` = 1.0** (экспортируется в JSON,
чтобы оценку можно было воспроизвести позже).

---

## 1. Что измеряется

Оценка **не означает безопасность**. Она означает: *сколько штрафа набрала
декларация по набору правил версии 1.0*. Ничего больше.

```
score = max(0, 100 − Σ penalty[severity])
penalty: critical 40 · high 15 · medium 6 · low 2
```

**100 — чисто** по выбранным правилам. **0 — не «нет риска», а насыщение:**
штраф превысил 100. Поэтому рядом со score всегда идёт `penalty_total` —
на насыщении по одной оценке не отличить три критические находки от двадцати.

---

## 2. Главное: почему одного числа мало

Потери в крипто приходят **не из кода**.

| Вектор | Доля стоимости потерь, 2025 |
|---|---|
| **Инфраструктура** (ключи, роли, мультисиг, governance) | **76 %** |
| Логика кода | 12 % |
| Дизайн / архитектура | 8 % |
| Экономика / недетерминированность | 4 % |

Источники — в разделе 7. Аудит кода закрывает ~12 % стоимости потерь;
остальное — компрометация контроля. Поэтому отчёт отдаёт разбивку:

```json
"vector_scores": {"infrastructure": 60, "logic": 100,
                  "design": 100, "economic": 100},
"vector_loss_share": {"infrastructure": 76, "logic": 12,
                      "design": 8, "economic": 4}
```

Страховщику нужно знать, **какой слой даёт убыток**, а не среднее по всем.

---

## 3. Доверие к оценке: `score_confidence`

Честность здесь важнее самой цифры. Правило, которому **не хватает полей**,
не имеет права молчать — оно попадает в `unverified`, а не в «чисто».

| Уверенность | Условие |
|---|---|
| `high` | все правила получили нужные поля |
| `medium` | 1–3 правила без данных |
| `low` | больше 3 правил без данных, либо ни одного правила не выполнено |

**Почему это защитимо:** заявка «всё чисто» при `confidence: low` —
это признание границ проверки, а не сокрытие пробела. Пробел, названный
своим именом, оспорить нельзя.

> Тест `test_missing_field_goes_to_unverified_not_clean` закрывает именно
> этот провал: раньше CI мог зеленеть впустую.

## 4. Чего эта оценка НЕ делает

Ограничения важнее достоинств. Ни одно из них нельзя убрать словами.

| # | Ограничение | Почему это важно |
|---|---|---|
| 1 | **Проверяется документ, а не ончейн-состояние.** Значения берутся из того, что выписали. Настоящий порог и настоящие владельцы — из сети | `infra.py` смотрит JSON. Реальное состояние требует RPC-режима, **которого нет** |
| 2 | **Нет калибровки на размеченном корпусе.** Веса взяты из долей потерь и здравого смысла, а не из регрессии по инцидентам | Это главный пробел. См. раздел 6 |
| 3 | **Нет вероятности.** Score — не вероятность потери. «62» не означает «62 % убытка» | Категориальная ошибка, самая частая при продаже |
| 4 | **Нет связи с премией.** Чтобы оценивать страховую ставку, нужен исторический убыток по похожим профилям | Вне области продукта |
| 5 | **Правила статичны.** Не выполняют код, не моделируют экономику, не строят граф вызовов | `delegatecall` поймаем текстом, порядок вызовов — нет |
| 6 | **Насыщение при 0 теряет порядок.** Три и двадцать критических находок дают одинаковый 0 | Отсюда `penalty_total` в отчёте |
| 7 | **Оценка невоспроизводима без версии весов.** Через год старый счёт не отличить от нового | Отсюда `score_version` |

**Это не формальная верификация и не замена аудита мультисига.**
Формулировка продублирована в `disclaimer` каждого вердикта.

## 5. Как оспорить — чтобы оспора не выиграли

Оценка должна выдерживать проверку, поэтому процедура открыта:

1. **Версия весов** — в отчёте. Спор идёт к конкретной версии, а не «к оценке вообще».
2. **Каждое правило** возвращает `why` (почему опасно) и `fix` (что делать). Находка без обоих не выпускается.
3. **Разделение по векторам** — видно, на чём именно построена оценка.
4. **`unverified` не чистый результат** — пробел заявлен явно.
5. **Отсутствие правила ≠ отсутствие дыры.** Правило не сработало, потому что паттерн не узнан, — не то же самое, что «уязвимости нет».

Пункт 5 означает: **отсутствие находок не является доказательством
безопасности.** Это написано, чтобы нельзя было процитировать «чисто»
как гарантию.

## 6. Что нужно, чтобы методика стала по-настоящему защитимой

Честный список недоработок, по убыванию ценности:

| Приоритет | Шаг | Критерий приёмки |
|---|---|---|
| 1 | **Размеченный корпус инцидентов**: конфигурации и контракты до взлома с размеченными векторами | ≥30 инцидентов, воспроизведение каждого тестом |
| 2 | **Веса из данных, а не из здравого смысла**: подогнать penalty под наблюдаемую стоимость потерь по severity | доля ошибок на корпусе ниже, чем у текущих весов |
| 3 | **RPC-режим**: сверять декларацию с ончейн-состоянием | расхождение декларации и сети ловится как находка |
| 4 | **Калибровка под отрасль**: разные веса для lending / DEX / мостов | веса разделены, тест на каждом профиле |
| 5 | **Версионирование истории**: хранить счёт с датой и версией | воспроизведение счёта года назад |

Пока пункты 1–3 не сделаны, **`score` — индикатор для внутреннего
использования, а не инструмент принятия страхового решения.**
